# 0002 — Claves primarias UUID v7 generadas en la aplicación

- **Estado:** aceptada
- **Fecha:** 2026-11-05
- **Etapa:** 01

## Contexto

La Parte 1 (§5) fija claves primarias UUID v7, ordenables por tiempo. Hay dos motivos.
Los UUID no revelan cuántos registros hay ni permiten adivinar ids de otra organización.
Y, a diferencia de los UUID v4, insertan al final del índice B-tree, así que no lo fragmentan.

El stack elegido no los genera de forma nativa: `uuid.uuid7()` llega en Python 3.14 y
`uuidv7()` en PostgreSQL 18. El proyecto usa Python 3.12 y PostgreSQL 16.

## Opciones consideradas

1. **Librería `uuid-utils` en Python 3.12**: implementación en Rust, rápida y con tipos.
   Su módulo `uuid_utils.compat` devuelve `uuid.UUID` estándar, compatible con Pydantic y SQLAlchemy.
2. **Subir a Python 3.14 y PostgreSQL 18**: v7 nativo, pero sale de lo definido en los planes.
   Además, algunas dependencias de etapas futuras (OCR, extracción) podrían tardar en soportarlo.
3. **Usar UUID v4**: nativo, pero aleatorio. Fragmenta el índice primario y no ordena por fecha.

## Decisión

Opción 1. Los ids los genera la aplicación con `app.shared.ids.new_id()`, que usa
`uuid_utils.compat.uuid7()`. Las tablas no tienen `DEFAULT` para el id.

## Consecuencias

- Los casos de uso reciben `id_factory` por inyección, así que los tests usan ids fijos.
- El id se conoce antes del `INSERT`, lo que sirve para encolar trabajos o armar rutas de storage (etapa 4).
- Si en el futuro se pasa a Python 3.14 o más, se reemplaza la librería por `uuid.uuid7()`.
  El cambio se limita a `app/shared/ids.py`.

## Evidencia

- `tests/unit/test_organization_use_cases.py::test_create_organization_uses_uuid_v7_by_default`
- `tests/integration/test_organizations_api.py::test_create_then_get_organization` verifica `version == 7` en lo que devuelve la API.
